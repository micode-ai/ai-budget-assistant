# Contact the developer — in-app support thread with two-way translation

Date: 2026-11-27 · Status: approved design, awaiting plan

## Intent

Today the only way a user can reach the developer is a `mailto:` link
(`apps/mobile/src/constants/legal.ts`). It drops the user out of the app,
carries no context, and the developer gets mail in eleven languages.

The developer wants users to write to him **from inside the app**, in any
language, and wants language to stop mattering in either direction:

- a message arrives **in the language it was written in** and **in the
  recipient's language** (when auto-translate is on);
- the developer reads and answers in Russian; the user gets the original reply
  plus a translation into their own language.

The concept was picked from three generated by Fable (a thread inbox, an
escalation from the AI chat, per-screen feedback). The other two are possible
later entry points into the same thread, not part of this work.

## Goals

1. A signed-in user opens one persistent conversation with the developer, from
   Settings and from the Help screen, on phone and desktop web (≥1024).
2. Every message stores its original text and detected language, plus a
   translation into the reader's language. The original is always one tap away.
3. The developer gets each new message instantly in a **dedicated support
   Telegram bot** and replies by *replying to that message* in Russian.
4. The admin dashboard has a **Support** page: all threads with full history,
   live updates, a reply box, and per-user mute and close. Admin is the source of truth;
   Telegram is a fast front door to it.
5. The user is told about a reply by push and an unread dot, and sees honest
   status on their messages (sent → read by the developer).

## Non-goals (v1)

- Image or file attachments (follow-up; needs storage and the
  `receiptImage.ts` downscaling path).
- Entry points from the AI chat or from the Telegram/WhatsApp/Slack bots (concept 2), and
  per-screen feedback with screenshots (concept 3).
- Offline queueing: sending needs a connection. Offline, the composer is
  disabled with an explanation. The thread is not an offline-first entity.
- E-mail fallback for unread replies, canned replies, multi-agent support, SLA
  tracking, retention policy.
- Guests (receipt-split, shopping-list, group links): no entry point.

## Anti-goals (a failure even if it works)

- Any financial data (amounts, transactions, account names, receipts,
  location) leaving the app automatically with a message.
- A translation shown **without** a way to see the original, because a
  mistranslated money term must stay checkable.
- The user's text being able to steer the model (prompt injection). Translation
  output never triggers tools or actions.
- Touching the shared ops bot (`OPS_TELEGRAM_*`), which other MiCode projects
  use. Support uses its own bot and token.
- A reply from the developer silently going to the wrong user.

## Approaches considered

| | Approach | Trade-off | Verdict |
|---|---|---|---|
| 1 | **Thread inbox** — one conversation per user, Telegram and admin on the developer side | the only one that is a real two-way conversation; reuses push, admin socket, OpenAI | **picked** |
| 2 | Escalation from the AI chat via a new tool | deflects easy questions, but replies get lost among ordinary chat | later entry point |
| 3 | Per-screen feedback sheet with a screenshot | rich context, but a one-shot report, awkward to answer | later entry point |

Reply channel for the developer, decided separately:

| | Option | Verdict |
|---|---|---|
| A | Admin only; Telegram only notifies, with a link | simplest, but each answer needs a browser |
| B | **Separate support bot** with its own webhook; reply-to-message in Telegram | **picked** — answering by reply is the main convenience, and it does not disturb other projects |
| C | Webhook on the existing ops bot | rejected: the ops channel is shared by several projects, and Telegram allows one webhook per bot |

## Design

### Data (Prisma, user-scoped — NOT account-scoped)

Support is between a person and the developer, so it hangs off `userId`,
like exchange-rate alerts. It is not behind `AccountContextGuard`.

- `SupportThread` — `id`, `userId` (unique: one thread per user), `status`
  (`open` | `closed`), `muted` (bool, set by the developer), `autoTranslate`
  (bool, default true — the **user's** toggle), `lastMessageAt`,
  `userUnreadCount`, `developerUnreadCount`, `createdAt`.
- `SupportMessage` — `id`, `threadId`, `author` (`user` | `developer`),
  `body` (original), `bodyLang` (detected ISO 639-1), `translatedBody?`,
  `translatedLang?`, `context` (JSON, user messages only), `telegramMessageId?`
  (the id of the card in the support chat, for reply mapping), `via`
  (`app` | `admin` | `telegram`), `readAt?`, `createdAt`.
- Both cascade-delete with the user (admin hard delete). Migration in the same commit (ABA-558).
- Self-deletion (`DELETE /users/me`) is a soft delete (`UsersService.deactivate`
  sets `isActive=false`), so the cascade never fires. **Decided:** deactivation
  hard-deletes the user's `SupportThread` (and its messages) inside the same
  transaction. Message text is personal data, and the history goes with it.
- A closed thread reopens when the user writes again **or when the developer
  replies**. *My call:* "closed" is an admin-side filter only; the user never
  sees a closed state.

### Lifecycle rules (*my calls*, from the builder check)

- **Mute:** a muted user's messages are still stored and visible in admin
  under a "Muted" filter. They are not sent to Telegram, do not bump
  `developerUnreadCount`, the nav badge or the socket event. They never get `readAt`, so the user's status
  stays "Sent" and the mute cannot be noticed. The developer can unmute, and can
  still reply from admin. Telegram refuses replies to a muted thread.
- **Replies to an inactive user** (`isActive=false`) are refused in both channels.
- **Push:** `support_reply` has no settings toggle, because it answers the
  user's own question, so no new `notify*` column. It still respects quiet hours
  like every push from `sendToUser`.
- **Cost:** translation is free on every tier and does **not** count against
  the user's AI usage limit. A user at their limit still gets translations.
  Its calls are recorded in AI cost tracking under a distinct feature name, so
  the admin AI-usage page shows what support costs.

### Translation

- Done **once, on write**, server-side, with `CHEAP_MODEL`
  (`model-resolver.ts`). One call returns JSON `{ detectedLang, translation }`
  with a strict schema, no tools, and a system prompt that treats the text as data to
  translate, never as instructions. The text goes in a delimited user turn.
- User → developer: target is `SUPPORT_DEVELOPER_LANGUAGE` (env, default `ru`).
- Developer → user: target is the user's UI locale (`user.language`, mapped
  through `toIntlLocale`-compatible codes; `br` means Brazilian Portuguese).
- If `detectedLang` equals the target, store no translation.
- If translation fails, the message is still stored and delivered, original
  only; a later view does not retry automatically (the developer can hit
  "translate" in admin).
- Length cap: 4000 characters per message.
- **The user's toggle** (`autoTranslate`, in the thread screen's header menu):
  on → translated reply shown first, "Show original" under it; off → original
  shown first, "Show translation" under it. The translation is stored either
  way.
- **The developer's toggle**: none in v1. The developer always sees the
  translation first with the original under it, in both Telegram and admin. A
  per-thread "original first" switch is left to the builder if it is cheap.

### Auto-attached context (user messages only)

App version (+ build sha on web), platform, OS version, UI locale, subscription
tier, current account type, and the route **pattern** of the screen the user
came from. Never: amounts, transactions, names of accounts or categories,
location, e-mail of other members. The user sees a collapsed "Attached:
app version, device, language" line under the composer.

All users, encrypted accounts included, see one line under the composer: the
message is stored on the server and translated by an AI service, so they should
not paste anything private. **My call:** no special case for
`encryptionTier >= 2`. A support message is something the user explicitly
writes to a person, not account data, so it does not fall under the chat's E2EE refusal.

### Support Telegram bot

- New env: `SUPPORT_TELEGRAM_BOT_TOKEN`, `SUPPORT_TELEGRAM_CHAT_ID` (the
  developer's private chat with the bot), `SUPPORT_TELEGRAM_WEBHOOK_URL` (base),
  `SUPPORT_TELEGRAM_WEBHOOK_SECRET`. Unset token → feature still works through
  admin, Telegram is skipped (log, no error).
- Webhook route `support-telegram/webhook`, added to
  `global-prefix-exclusions.ts`. Verify `X-Telegram-Bot-Api-Secret-Token`
  with a timing-safe compare (same as the assistant bot, ABA-626). Accept
  updates **only** from `SUPPORT_TELEGRAM_CHAT_ID`; drop everything else.
- Outbound card per user message: Russian translation, then original with its
  language, the context line, the user's name and id, and a link to the
  admin thread. Its `message_id` is stored as `telegramMessageId`.
- The developer replies with Telegram's reply. `reply_to_message.message_id`
  resolves the message and its thread. A message that is not a reply,
  or replies to an unknown card, is **never guessed**: the bot answers "reply
  to a user's card to answer them".
- After a reply is delivered, the bot confirms with the translation the user
  will see ("✓ sent to Anna · Polish: …"), so the developer can check it.
- A reply to a muted or deleted user's thread is refused with a message.

### Admin — Support page

`apps/admin/src/app/support/`: thread list (unread first, then by
`lastMessageAt`), a thread view with bubbles (translation first, original
under it, context panel), a reply box, and mute/close/reopen. Live updates go through
the existing `AdminGateway` (Socket.io). Opening a thread marks user messages
`readAt` and zeroes `developerUnreadCount`. A reply sent from Telegram marks
the thread read too. Unread count shows in the admin nav.

### API

Module `modules/support/`.

- User routes (`JwtAuthGuard` only): get my thread with messages (paged),
  send a message, mark read, toggle `autoTranslate`.
- Admin routes (`AdminGuard`): list threads, get a thread, reply, mute,
  close/reopen, re-translate a message.
- Send rate limit: 10 messages per user per 24 h through
  `CacheService.incrementWindow`, **failing closed**. A muted user gets the same
  "sent" response, and nothing is forwarded (shadow mute).
- Forwarding to Telegram and push are fire-and-forget with
  `logFireAndForget` (ABA-461). The message row is committed first.

### Mobile and web app

- Entry: a "Write to the developer" row in Settings (with an unread dot) and
  a button on the Help screen. The `mailto:` stays as a secondary link in About.
- Screen `app/support.tsx` with a header (title + back). Phone: chat
  bubbles, a composer, and the status under the user's last message: "Sent" /
  "Read by the developer" · "Usually replies within a day". Desktop web ≥1024:
  a centred reading column in the desktop chat screen's language (component-level
  `.web.tsx` split, never route-level).
- Push type `support_reply` → deep link to `/support`, handled by its own
  hook in `src/hooks/` (not a new `useEffect` in `_layout.tsx`).
- Data loads from the API on open and on focus, with no SQLite mirror. Offline
  → read-only with a banner.
- New strings in all 11 locales. Help section in `user_docs/` (all locales).

## Constraints the builder must respect

- No runtime imports from `@budget/shared-*` in the API.
- Schema change and migration in one commit.
- Bottom-anchored composer clears `insets.bottom`.
- Push data key must not be `type` alone (it is overwritten by `NotificationsService`); use a distinct key.
- Wiki page `docs/wiki/features/contact-developer.md` with Invariants.
