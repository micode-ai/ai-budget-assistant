# API rate limit (nginx) — ABA-522

The web app's cold start was being rate-limited by nginx, and the rejection was
invisible to the browser. This is what was changed, why, and how to undo it.

**The config is not in this repository.** It lives on the VPS, in
`shared-nginx`, which also serves eksiegowyai, marketing and accounting — so
every change here affects a machine several projects share. See the
`prod-vps-ssh-access` memory for access.

## The symptom, and why it took so long to explain

A fresh session (incognito, or any browser with nothing cached) loaded the
dashboard with no data at all. Every store's pull failed with:

```
TypeError: Failed to fetch
```

No status code, no CORS error, nothing in the API logs. Meanwhile the *same*
endpoints answered `200` in 200–450 ms when called one at a time from the same
page seconds later. That contradiction is what made this look like a client
bug for days — it was investigated three times (ABA-518, ABA-519, ABA-520) and
each time written up as "not explained".

The answer was in nginx's error log, not the browser:

```
[error] limiting requests, excess: 20.150 by zone "budget_api",
  client: <ip>, server: api.ai-budget.pl,
  request: "GET /api/v1/wallet/summary HTTP/1.1",
  referrer: "https://app.ai-budget.pl/"
```

Two facts combine into an invisible failure:

1. **The dashboard's cold start is a burst of ~30–40 requests.** Every
   account-scoped GET carries `Authorization` + `X-Account-Id`, which makes it
   a non-simple CORS request — so each one is preceded by an `OPTIONS`
   preflight. The effective count is roughly doubled.
2. **nginx's own error response carries no CORS headers.** The old config used
   the default `limit_req_status` (503). A 503 generated by nginx never passes
   through the API, so it has no `Access-Control-Allow-Origin`, and the browser
   is not allowed to show the response *at all* — it surfaces as
   `TypeError: Failed to fetch` with no status. To the client, a throttled
   request and a dead network are indistinguishable.

**Native was unaffected**, which is why the mobile app always looked correct:
it makes no preflights (halving the count), and SQLite serves every screen
even when the pulls fail, so the failures were invisible rather than absent.

## What changed

`/opt/shared-nginx/nginx.conf` (http level):

```nginx
map $request_method $budget_limit_key {
    default  $binary_remote_addr;
    OPTIONS  "";              # empty key ⇒ limit_req skips the request
}

map $http_origin $budget_cors_origin {
    default                    "";
    "https://app.ai-budget.pl" $http_origin;
    "https://ai-budget.pl"     $http_origin;
}

limit_req_zone $budget_limit_key zone=budget_api:10m rate=30r/s;   # was 10r/s
```

`/opt/shared-nginx/conf.d/ai-budget.conf` (the `api.ai-budget.pl` server):

```nginx
limit_req_status 429;
error_page 429 = @budget_throttled;

location @budget_throttled {
    add_header Access-Control-Allow-Origin  $budget_cors_origin always;
    add_header Access-Control-Allow-Headers "Authorization,Content-Type,X-Account-Id" always;
    add_header Access-Control-Allow-Methods "GET,POST,PATCH,PUT,DELETE,OPTIONS" always;
    add_header Retry-After 1 always;
    add_header Content-Type application/json always;
    return 429 '{"statusCode":429,"message":"Too many requests"}';
}

location / {
    limit_req zone=budget_api burst=60 nodelay;   # was burst=20
    ...
}
```

Three rules worth keeping:

- **The CORS headers belong in the named location only.** Putting them in
  `location /` would duplicate the API's own `Access-Control-Allow-Origin` on
  every successful response, and two of that header is an invalid CORS
  response — it would break every request instead of fixing the throttled one.
- **`$budget_cors_origin` is a whitelist, never `$http_origin` passed
  through.** nginx omits an `add_header` whose value is empty, so an unknown
  origin simply gets no header.
- **The `api` and `marketing_api` zones are untouched.** They belong to other
  projects on this nginx.

## Applying a change (the part that wastes an hour)

`nginx.conf` is a **single-file bind mount**. Two consequences:

1. **Do not use `sed -i`.** It writes a temp file and renames, which replaces
   the inode; the container keeps reading the old file. Truncate in place
   instead — `python3` opening with `"w"`, or `cat new > nginx.conf`.
2. **`nginx -s reload` and `SIGHUP` did not apply the change.** Both were sent,
   both reported success, and the worker PIDs never changed — verified by
   `docker exec shared-nginx ps` before and after, and by measuring the
   effective limit (still ~28 of 50 requests passing). Only
   `docker restart shared-nginx` cycled the workers.

`docker restart` drops every site on the box for 1–3 seconds. Check all of them
afterwards, not just this project's:

```bash
docker restart shared-nginx && sleep 5
for u in https://api.ai-budget.pl/api/v1/health https://app.ai-budget.pl \
         https://ai-budget.pl https://admin.ai-budget.pl https://eksiegowyai.pl; do
  printf "%-45s " "$u"; curl -s -o /dev/null -w "%{http_code}\n" --max-time 10 "$u"
done
```

**Always `docker exec shared-nginx nginx -t` before restarting.** Note what it
does *not* prove: it validates whatever the container currently reads, so it
passes just as happily on the old config. It catches a syntax error; it does
not confirm your edit landed. For that, `grep` the file from inside the
container.

## Verifying

Measured after the restart, from a fresh connection (the browser's keepalive
connections stay pinned to the old workers, so testing from the open app
measures the *old* config):

```bash
# Before: 31×200, 19×503.  After: 50×200.
for i in $(seq 1 50); do
  (curl -s -o /dev/null -w "%{http_code}\n" --no-keepalive --max-time 15 \
     https://api.ai-budget.pl/api/v1/health) &
done | sort | uniq -c

# Preflights are exempt: 80×204, none limited.
for i in $(seq 1 80); do
  (curl -s -o /dev/null -w "%{http_code}\n" --no-keepalive -X OPTIONS \
     https://api.ai-budget.pl/api/v1/expenses \
     -H "Origin: https://app.ai-budget.pl" \
     -H "Access-Control-Request-Method: GET") &
done | sort | uniq -c
```

**The 429 path is deployed and syntactically valid but has NOT been observed.**
250 requests at 120-way parallelism all returned 200 — the new limit is hard to
reach from one machine, which is the point of the change but also means the
error path is untested in practice. It is a safety net for the next time
someone does exceed it: if a throttled request ever shows up as a bare
`Failed to fetch` again, that is the first thing to check.

## Rollback

Backups are timestamped beside the originals:

```bash
cd /opt/shared-nginx
cat nginx.conf.bak.ratelimit.20260909-104119 > nginx.conf
cat conf.d/ai-budget.conf.bak.ratelimit.20260909-104119 > conf.d/ai-budget.conf
docker exec shared-nginx nginx -t && docker restart shared-nginx
```

## Still open

The dashboard fires **more than twenty endpoints at once** on a cold start.
Raising the ceiling made that survivable; it did not make it reasonable. A
client-side change — batching, staggering, or simply not fetching everything
before the first paint — is the real fix, and would also make the app faster
for the user rather than merely legal at the proxy. Tracked in ABA-522.
