# AI Budget Assistant

## This file is the schema; the knowledge lives in `docs/wiki/`

Start at **[`docs/wiki/index.md`](docs/wiki/index.md)** — a hub per domain, a page per feature,
one shape per page whose `Invariants` section states what must not break and why.

This file keeps only what belongs to no single feature: repo-wide rules and conventions,
cross-cutting patterns, environment variables, deploy and release procedure. **Do not append a new
feature's description here** — it goes on a wiki page. When you touch a feature that is still
described in this file, move it to its page as part of that task and leave a short pointer behind
(design decision 2: the migration runs one feature per task, never as a big-bang pass).

Three rituals keep it alive, one per operation:

- **Ingest** — the `finish-aba-task` skill: issue → wiki page → one line in
  [`docs/wiki/log.md`](docs/wiki/log.md) → this file only if a repo-wide rule changed → user docs.
- **Query** — the `wiki-query` skill: **read the wiki before the code**, answer with the page path
  cited, and file the finding back when the investigation cost real effort — *even if no code
  changed*. A diagnosis ending in "this is working correctly" leaves no commit and no issue behind
  it, so without this it leaves nothing at all and gets re-investigated.
- **Lint** — `python scripts/wiki-lint.py` (links, cited paths, orphans) and
  `scripts/wiki-staleness.py` (pages the code has moved past) run weekly via `wiki-audit.yml` and
  comment on the **Wiki audit** issue. They run no model — this project's Claude Code is on a
  subscription, so CI has no key. The reading half is the `wiki-audit` skill, run in a session.

Why: this file reached 77k words (~104k tokens) loaded whole into every session, while
`docs/wiki/` — bootstrapped once in May and never ingested into again — had drifted into stating
"11 AI functions" when there were 18. The artifact was never the problem; the missing loop was.
Design: [`docs/superpowers/specs/2026-09-22-llm-wiki-design.md`](docs/superpowers/specs/2026-09-22-llm-wiki-design.md).

## Architecture

Turborepo monorepo with 5 packages:

| Package | Tech | Purpose |
|---|---|---|
| `apps/api` | NestJS 10 + Prisma 5 + PostgreSQL + Redis | REST API backend |
| `apps/mobile` | Expo 54 + React Native 0.81 + Zustand + SQLite/Drizzle | Mobile app (iOS/Android/Web) |
| `apps/admin` | Next.js 16 + React 19 + TailwindCSS 4 + shadcn/ui + Recharts | Admin web dashboard (port 3001) |
| `packages/shared-types` | TypeScript interfaces | Entities and DTOs shared between api and mobile |
| `packages/shared-utils` | Zod schemas + formatting + constants | Validation and utilities shared between api and mobile |

## Key Patterns

### API (NestJS)
- **Module structure**: `modules/<feature>/` contains `<feature>.module.ts`, `<feature>.controller.ts`, `<feature>.service.ts`, `dto/index.ts`, `guards/`
- **Auth**: JWT via `@UseGuards(JwtAuthGuard)`. Request type: `AuthenticatedRequest` from `common/types/index.ts`. Registration, email verification, password reset, email change and Google sign-in (ABA-282, ABA-291) are on the wiki hub — `docs/wiki/auth.md`. Carried here: a passwordless (Google-only) account must be rejected before any `bcrypt.compare` — `login()` and `changeEmailRequest()` both check `passwordHash` first; auto-link to an existing account happens only on a Google-verified email; and the web Google request must pass a `nonce` (`extraParams`), which the generic `useAuthRequest` does not add.
- **Restore credentials / Android session restore (ABA-464 server, ABA-465 client)**: a real WebAuthn credential so a signed-in session survives an Android device transfer, for Google Play's April-2027 requirement. **Moved to the wiki** — `docs/wiki/features/restore-credentials.md`. Carried here: registration fires on EVERY authenticated launch, not only after sign-in — `JWT_EXPIRES_IN` is 7 days and the app otherwise restores its session from local storage indefinitely, so the launch path is the only one that reaches the installed base; and `web-deploy.yml` fails the whole job, not just the apex rsync, if `docs/ops/assetlinks.json` ever holds a `REPLACE_WITH_*` placeholder.
- **Last-active tracking (ABA-389)**: `User.lastSyncAt` is the last-ACTIVITY stamp (admin "Last Active", DAU/WAU, referral qualification), written by `JwtStrategy.validate()` through `LastActiveService.touch`. **Moved to the wiki** — `docs/wiki/features/last-active-tracking.md`. Carried here: **do not re-add a per-route `updateLastSync` call** — only the public `login`/`googleLogin`/`refreshToken` routes stamp explicitly, because they never reach `JwtStrategy`; and the throttle goes through `CacheService.setIfAbsent`, which returns `false` on a Redis outage so the stamp is skipped rather than written on every request.
- **Account scoping**: `AccountContextGuard` (a **guard**, `implements CanActivate`, despite living in `common/middleware/account-context.middleware.ts` — there is no `AccountContextMiddleware` class) reads the `X-Account-Id` header, resolves membership, adds `accountId` and `accountRole` to request
- **Role-based access**: `AccountRoleGuard` with `@RequireRole('owner'|'editor')` decorator (DI-based, needs `AccountsModule`). `ViewerBlockGuard` (ABA-155) — zero-dependency guard in same file; use as `@UseGuards(new ViewerBlockGuard())` on any write method without importing `AccountsModule`. Reads `req.accountRole` set by `AccountContextGuard`. Apply to all POST/PATCH/PUT/DELETE endpoints that mutate account-scoped data. AI chat: viewer write-actions blocked in `chat.service.ts` before a pending action is queued. Bots: `TelegramUserState` and `WhatsAppUserState` include `accountRole`; link services join `AccountMember` on `getLink()`; write handlers check the role before executing.
- **Service signature**: `(accountId, userId, dto)` as parameters, all Prisma queries filter by `accountId`
- **Transaction attribution**: every expense/income response carries `createdByUserName`, flattened from the creator's `userId`. **Moved to the wiki** — `docs/wiki/features/expenses-service.md`. Carried here: always pass the `user: { select: { name: true } }` include and map through `toExpenseResponse`/`toIncomeResponse`; and when typing a `where`, build the date range in its own `Prisma.DateTimeFilter` — `WhereInput['date']` can be a bare `Date`, so spreading it fails to typecheck.
- **Database**: Prisma ORM. Schema at `apps/api/prisma/schema.prisma`. Uses `@map("snake_case")` for column names. Prod `DATABASE_URL` includes `connection_limit=10` (see `docker-compose.prod.yml`) to cap the connection pool. **A `schema.prisma` field change MUST land with its migration in the same commit — nothing in the pipeline catches a missing one (ABA-558)**: lint, typecheck, tests and the deploy all pass, `prisma generate` happily builds a client that selects the new column, `prisma migrate deploy` has nothing to apply, and the first query to touch it fails at runtime in production. ABA-556 added `ExpenseItem.lineDiscount` without a migration and broke `ExpensesService.findAll` — the whole transactions list, not just the receipt-split feature it shipped — for everyone. **Monitoring cannot see this**: `/health` runs `SELECT 1` and never touches the table, so the container reported `healthy` and `uptime-check.yml` stayed green throughout; Sentry was the only signal. To recover, author the migration and apply it through the **standard `migrator` service** (`docker compose -f docker-compose.prod.yml --env-file .env.production --profile migrate run --rm migrator`, the same command `scripts/deploy.sh` runs) after copying the migration folder to `/opt/ai-budget` — never by hand-editing the database, which leaves `_prisma_migrations` without the row and makes the next deploy re-apply it. To audit for drift without a shadow DB, diff the `@map`ped columns in `schema.prisma` against `information_schema.columns` on prod; note a `String[]` field has no `@db` column type of its own and will read as a false positive.

- **Caching layer** (ABA-151): `common/cache/cache.service.ts` — global `@Global()` ioredis wrapper; `delByPrefix` uses cursor-based `SCAN` (not blocking `KEYS`). `common/cache/redis-throttler-storage.ts` — `RedisThrottlerStorage` (`ThrottlerStorage` v5 interface, INCR+PEXPIRE NX+PTTL pipeline, `keyPrefix: 'throttle:'`); registered via `ThrottlerModule.forRootAsync` in `app.module.ts` so rate limits survive restarts. **`CacheService.incrementWindow(key, windowMs)`** (ABA-416) is the general-purpose version of the same INCR+PEXPIRE-NX pattern for any security-sensitive rate limit that needs to live outside `ThrottlerModule` — unlike every other `CacheService` method it does NOT swallow Redis errors (callers must fail closed, not silently allow unlimited attempts on a Redis outage). First consumer: `EncryptionService.checkRecoveryRateLimit` (`enc:recovery:{email}`, 5/15min) — replaced a plain in-memory `Map` that reset on every deploy, the same defect class as the still-open `auth.service.ts` rate-limit Maps (tech-debt `auth-rate-limit-in-memory-maps`, not yet fixed).
- **Fire-and-forget logging convention (ABA-461)**: any `void someCall().catch(...)` guarding a non-critical side effect (Family Feed events, anomaly checks, gamification, renewal/reminder pushes, wallet-currency backfills, community-price contributions, etc.) MUST log the rejection, never swallow it with `.catch(() => {})` — a silent failure there means the secondary effect never happened and there's no way to diagnose it. Use `logFireAndForget(this.logger, 'ClassName.whatItDoes')` from `common/utils/fire-and-forget.ts`, which returns a `.catch()` handler that calls `Logger.warn` (never `.error` — mirrors the mobile ABA-157 convention that a fire-and-forget failure is expected/transient, not exceptional). Every call site across the API (`subscriptions`, `expenses`, `incomes`, `wallet`, `budgets`, `purchase-requests`, `import-bank`, `import-wise`, `sync`, `referrals`, `telegram`, `community-prices`, `insights`, `shopping-list`, `trip-settle-up`, `debts`, `gamification`, `user-subscriptions`) was migrated to this helper; a new fire-and-forget call site should use it too, not a bare empty `.catch()`.
- **Daily cron pagination** (ABA-457): `common/utils/paginate.ts` — `paginateById(fetchPage, batchSize=500)`, a generic async generator that streams a Prisma `findMany`-shaped query in `id`-ordered batches (`orderBy:{id:'asc'}` + `cursor`/`skip`) instead of loading the whole eligible-row set in one call. Consumed by all 5 daily notification crons that used to `findMany` an entire table (tech-debt `daily-crons-full-table-scan`): `tracking-gap-reminder.cron.ts`, `debt-reminder.cron.ts` (both methods — the per-batch repayment lookup is scoped to that batch's debt ids, not the whole day's set), `expense-recurring.cron.ts` (see below — its recurringId-dedup switched from "first-seen wins" under a global `orderBy:date desc` to "latest-date wins" compared per row, since pagination is now by `id`), `subscription-renewal.cron.ts` (both crons), `trial-reminder.cron.ts`. New cron/batch-job code that scans an unbounded table should use this util rather than a bare `findMany`. Deliberately NOT changed: `NotificationsService.sendToUser`'s per-user `findUnique` re-fetch (N+1) — that method has many other callers and its signature was out of scope for this fix.

## Dependency Order for Changes

When modifying features that span multiple packages, follow this order:

1. `packages/shared-types` — entity interfaces and DTOs
2. `packages/shared-utils` — Zod validation schemas (if needed)
3. `apps/api/prisma/schema.prisma` — database schema, then `npx prisma migrate dev --name <name>` + `npx prisma generate`
4. `apps/api/src/modules/*` — API services, controllers, guards
5. `apps/mobile/src/db/schema/index.ts` — SQLite schema (independent from API DB)
6. `apps/mobile/src/db/*Repository.ts` — data access layer
7. `apps/mobile/src/stores/*` — Zustand stores
8. `apps/mobile/src/services/api.ts` — API client methods
9. `apps/mobile/app/*` — screens and UI
10. `apps/mobile/src/i18n/locales/*.ts` — translations (all 9 files)

Mobile SQLite changes (step 5-6) are independent from API Prisma changes (step 3-4) and can run in parallel.

ALL operational Telegram alerts go here, NOT the assistant bot: `TelegramService` (the ops notifier in `modules/telegram/`, injected by auth/subscriptions/referrals/import-bank) reads these for new-registration / new-subscription / referral / request-a-bank alerts, and `uptime-check.yml`/`backup-db.yml`/`infra-watch.yml` use the same-named **GitHub Actions secrets** for downtime/backup/infra alerts. **No fallback** — if `OPS_*` is unset, ops alerts are skipped (never leak to the assistant bot). ## Production

Hetzner VPS (Hetzner cloud), Docker Compose. Stack defined in `docker-compose.prod.yml`:
- `budget-db-prod` (postgres:16-alpine, 512M), `budget-redis-prod` (redis:7-alpine, 320M — `maxmemory 256mb allkeys-lru`), `budget-api-prod` (1G, `NODE_OPTIONS=--max-old-space-size=768`), `budget-admin-prod` (256M), plus shared `accounting-nginx` (separate stack) reverse-proxying `api.ai-budget.pl` and `admin.ai-budget.pl`. API container has **no host port mapping** — reach it only through nginx or the docker network. **API memory (ABA-163)**: without an explicit `NODE_OPTIONS=--max-old-space-size`, Node auto-caps the V8 heap at ~half the container limit (~256M at 512M), which OOM-crashed the backup export. Compose sets heap to 768 and `deploy.resources.limits.memory` to 1G — keep them in sync (heap + ~150M non-heap must fit under the limit).
- **Inbound mail container (ABA-644)**: `budget-inbound-mail-prod` (`apps/inbound-mail`, receive-only SMTP for forwarded e-receipts) is behind the compose profile `inbound-mail` and is never started unless `.env.production` has `INBOUND_MAIL_CONTAINER=true`. It publishes host port **25** (IPv4, which bypasses `ufw`), has no `env_file`, and sits only on the isolated `inbound-mail-net` network shared with `api` — no route to Postgres or Redis. Runbook and activation steps: `docs/ops/inbound-mail.md`; feature: `docs/wiki/features/inbound-e-receipts.md`.
- Volumes: `ai-budget_postgres_data`, `ai-budget_redis_data` (preserve across deploys; never `docker volume prune` without filters).
- **DB backups (ABA-163, Phase 1)**: `.github/workflows/backup-db.yml` — nightly cron (`0 2 * * *` UTC, off-host so it survives a VPS outage) + `workflow_dispatch`. SSHes to the VPS, runs `pg_dump -Fc` inside `budget-db-prod`, streams it to the runner, validates it (size ≥10 KB + `pg_restore --list` object count), `age`-encrypts (asymmetric — runner holds only `AGE_PUBLIC_KEY`; the private key is **offline**, never in CI), and publishes it as a Release asset (`ai_budget-YYYY-MM-DD.dump.age`, tag `backup-YYYY-MM-DD`) in the private repo `BACKUP_REPO` via `BACKUP_REPO_TOKEN` (PAT, `contents:write`). Logic lives in `scripts/backup-db.sh` (dump+sanity+encrypt; mockable via `LOCAL_DUMP`) and `scripts/prune-backups.sh` (GFS retention 7 daily/4 weekly-Sunday/6 monthly-1st; mockable via `RELEASES_FILE`/`DRY_RUN`). Failure → Telegram alert (same pattern as `uptime-check.yml`). Restore: `docs/ops/restore-runbook.md` (decrypt → scratch-restore → verify → prod `pg_restore --clean --if-exists`). RPO ≤24 h. Redis is **not** backed up (cache/ephemeral). Receipt images are in-DB `Bytes`, so the dump captures them (and grows with them — revisit object storage if a dump exceeds a few hundred MB). Phases 2–4 (infra fault tolerance, HA, mobile local backup) deferred — see `docs/superpowers/specs/2026-05-29-postgres-backup-phase1-design.md`.
- Deploy: push to `development` triggers `.github/workflows/deploy.yml` → SSH → `scripts/deploy.sh` (`git reset --hard`, `npm install` with lock, build, `prisma migrate deploy`, `up -d --force-recreate api admin`, then `docker image prune -f` + `docker builder prune -af`). Verify-step polls `https://api.ai-budget.pl/api/v1/health` for up to 120 s. **Pre-deploy guard (ABA-317)**: `deploy.yml` runs `scripts/check-no-shared-utils-runtime-import.sh` on the runner *before* the SSH step — a runtime `import`/`require` of `@budget/shared-utils` in `apps/api/src` fails the deploy (the API has no build step for workspace packages, so it loads the shared-utils TS barrel and prod Node ESM crash-loops on `ERR_UNSUPPORTED_DIR_IMPORT`). Mirrored by an `apps/api` ESLint `no-restricted-imports` rule (`allowTypeImports`). `import type` is fine; copy runtime values into an API-local util. **Build-cache pruning matters**: images are built on the VPS each deploy and the build cache accumulated ~4 GB → disk hit 89% (ABA-165); the per-deploy `builder prune` is NOT enough on its own — **`deploy.yml` is path-filtered** (`apps/api/**`, `apps/admin/**`, `packages/**`, `docker/**`, `docker-compose.prod.yml`, `scripts/deploy.sh`), so a stretch of mobile/marketing/docs work means `deploy.sh` never runs and the cache grows untouched. That is how ABA-165 recurred as **ABA-432** a week after the last API deploy: 3.35 GB of cache + a 1.8 GB `buildkit/metadata_v2.db` put `/` at 88%. The scheduled **`.github/workflows/docker-gc.yml`** (`scripts/docker-gc.sh`, Sunday 01:00 UTC an hour before `backup-db.yml`, plus `workflow_dispatch`) is what actually bounds it; it no-ops below 70% and alerts only when the disk is **still** above 85% after cleaning. `.github/workflows/infra-diagnostics.yml` (manual `workflow_dispatch`) dumps a `docker system df` + `du` breakdown over SSH when disk needs investigating. **One Docker daemon is shared with `marketing-ai-*`, `accounting-*`, `legalka-bot` and `shared-nginx`, so `docker volume prune` (any filter) and `docker image prune -a` are both forbidden here** — the volumes include `ai-budget_postgres_data`, and unused-but-tagged images are another project's rollback target. Runbook: `docs/ops/disk-pressure.md`.
- **Snap-installed Docker is held and disabled** (`snap refresh --hold docker`, `snap disable docker`) after the 2026-04-27 incident where snap auto-refresh hijacked `/var/run/docker.sock` from the apt-installed daemon. Do not re-enable snap docker; only the apt-installed `dockerd` (system data root `/var/lib/docker`) owns prod state.
- Adding env vars: `docker restart` does NOT reload `env_file`. Must `docker compose -f docker-compose.prod.yml --env-file .env.production up -d --force-recreate <service>`.
- **CORS (ABA-151)**: `main.ts` builds `corsOrigins` from `process.env.CORS_ORIGIN.split(',')` (falls back to `localhost:8081`/`:3001` when unset). It must be an **explicit comma-separated origin list** in prod `.env.production` — e.g. `CORS_ORIGIN=https://admin.ai-budget.pl,https://ai-budget.pl`. Do **NOT** use `CORS_ORIGIN=*`: it becomes the array `["*"]`, which Express/Nest `cors` matches as a literal origin (not a wildcard), so the admin browser gets no `Access-Control-Allow-Origin` and login silently breaks (and `*` is invalid with `credentials:true`). Native mobile is unaffected (no `Origin` header). After changing it, force-recreate the `api` service (see env-var note above).

## Mobile releases (Android)

- **Bare Expo workflow** — `apps/mobile/android/` is committed, so EAS builds from the native project and does **not** run prebuild or read `app.json` for the version. The version shown in **Google Play comes from `apps/mobile/android/app/build.gradle` `versionName`**, not `app.json`. `eas.json` `appVersionSource: "remote"` + production `autoIncrement: true` only manage the integer `versionCode` (build number) remotely; they never touch `versionName`. (Historically this caused every release to ship as `1.0.0` while `versionCode` quietly incremented — ABA-131.)
- **Before each release**: bump `versionName` in `android/app/build.gradle` (source of truth for Play) AND `version` in `app.json` (kept in sync for the in-app update gate) to the same value. Do not hand-edit `versionCode` — EAS remote autoIncrement owns it.
- **One semver, two cadences — the web carries a build id and native does not (ABA-514).** Native and web are ONE codebase and ONE `app.json` version, and they must stay that way: a different scheme would invent a distinction the source does not have and break the only thing the number is for, tying a bug report to code. What they do not share is a release cadence — `web-deploy.yml` deploys on every push to `development`, while a phone carries whatever last cleared Play review (weeks here, and once frozen outright by the foreground-service declaration, ABA-438). So a bare shared number claims two different builds are the same software, and it already did: the deployed web app read `1.25.0` while carrying commits that were in no store build. **The web therefore shows `<version>+<short sha>`** — `EXPO_PUBLIC_BUILD_SHA`, set by `web-deploy.yml` from `github.sha`, composed by pure `src/features/about/displayVersion.ts` and rendered in the **existing** version row on the About screen (no new i18n key — a second row would need nine locales for a developer-facing string). `+` is semver **build metadata and is explicitly ignored for precedence**, so nothing that compares versions can see it: not `UpdatePrompt`/`useAppVersionCheck`, not `minSupportedVersion`, not the store-review throttle. Native passes no sha and keeps the bare version, because Play owns that string and `versionCode` is its own build identity. `displayVersion` **drops a non-hex build id rather than showing it** (the value comes from an env var, which can hold anything — including an un-expanded `${{ github.sha }}`); 7 characters, matching git's own abbreviation. **Do NOT add a `web` platform to the app-versions gate**: that gate exists because a native install can be arbitrarily old and needs forcing forward, whereas a web reload is always current — it would be a mechanism with no failure mode to prevent.
- **CI guard**: `apps/mobile/scripts/check-release-version.js` runs as a production-only step in `mobile-build.yml` and `mobile-eas-build.yml`. It fails the build if `build.gradle` versionName ≠ `app.json` version, and if the version isn't strictly greater than the latest `v*.*.*` git tag (skipped only when the repo truly has no release tags). Both workflows must check out with `fetch-tags: true`: without it the script saw no tags, logged "skipping", and 1.32.0 reached Play twice (2026-09-27 and 2026-10-01) — two builds a phone shows identically. The About screen now shows `versionName (versionCode)` on native for exactly that case (ABA-629).
- **Publish**: run the *Mobile Build & Publish* workflow (`mobile-build.yml`, profile `production`, submit `true`) → builds AAB `--local` → `eas submit` to the Play production track. After release, also add the new version in **admin → App Versions** so the in-app `UpdatePrompt` knows about it.
- **Foreground-service declaration blocks the submit, and no amount of retrying fixes it (1.18.0; unblocked on `development` since ABA-438)**: while the app declares `FOREGROUND_SERVICE_LOCATION` (Shopping Mode, ABA-408), `eas submit` fails at the *track update* step — the AAB uploads fine — with `Google Api Error: Invalid request - You must let us know whether your app uses any Foreground Service permissions.` fastlane retries it five times and every attempt fails identically, because this is a **Play Console form, not an API field**: Android 14+ requires a per-FGS-type declaration under **Play Console → the app → Policy → App content → Foreground service permissions**, stating what the feature does, why it must run as a foreground service, and (for the `location` type) usually a short video of the in-app journey. It is declared **per app, not per release**, so once filled in it stops blocking future submits. Recovery without rebuilding: the workflow already uploaded the AAB as the `app-release-production` GitHub artifact (30-day retention) — fill in the declaration, then upload that same file by hand in Play Console. A re-run of the workflow also works but burns another remote `versionCode`. Not to be confused with the much heavier `ACCESS_BACKGROUND_LOCATION` declaration, which this app deliberately does not need. **`development` no longer declares either permission** — ABA-438 moved Shopping Mode to `feature/shopping-mode` precisely so releases stop being hostage to this form — so a submit from the mainline works again without it. The declaration still has to be filled before that branch can re-land, and it is per app, not per release, so filling it early costs nothing.
- **Samsung Galaxy Store is a second, signature-separate channel (ABA-495)**: runbook `docs/ops/samsung-galaxy-store-rollout.md`. Two facts that decide everything else. (1) Since **2026-09-02** Samsung blocks *every* Seller Portal submission whose binary is not ADV-approved (unconditional — not the country-scoped install block of 2026-09-30), so the certificate signing the Galaxy Store build must first be added under **Play Console → Android developer verification → `com.budget.assistant` → Add key**; that package is registered with **1 key** today (Play App Signing, 2026-04-10). (2) Play App Signing holds our app signing key and will not export it, so a Galaxy Store build is signed with the **upload key** instead — same package, different signature, therefore **mutually exclusive installs** with the Play version and no updates crossing between stores, permanently. Verified as *not* signature-bound, so nothing breaks: Google sign-in uses the **web** OAuth client via the `ai-budget.pl/oauth/callback/` relay (`EXPO_PUBLIC_GOOGLE_ANDROID_CLIENT_ID` is dead config, read nowhere), and `google-services.json` carries no `oauth_client`/`certificate_hash` at all. The binary needs no code change — *Mobile Build & Publish* with `profile=preview, submit=false` already yields a production-API release APK (`app-release-preview` artifact), since every submit step is gated on `profile == 'production'`. Listing copy cannot be pasted from `docs/marketing/copy/google-play-listings.md` unchanged: Galaxy Store counts **bytes**, and `shortDescription` is **40 bytes** against Play's 80 chars, so all 9 locales are over (ru/ua/be by 63–67 B — UTF-8 Cyrillic leaves ~20 letters); screenshots must be ≤ **2:1**, and ours are 1080×2340 (2.17:1), so they pad to 1170×2340. Registration is free, but commercial-seller validation needs a company-domain e-mail (not the gmail Play login) plus MICODE documents, at up to 10 business days per stage. F-Droid is permanently ineligible — `LICENSE` says proprietary, not open source.

## Observability

- **Health**: `GET /api/v1/health` (public, no auth) — runs `SELECT 1` on Postgres, returns `{status, db, uptimeSeconds, timestamp}`. 503 if DB fails. Used by Docker `HEALTHCHECK` (requires HTTP 200) and CI verify-step.
- **Uptime**: `.github/workflows/uptime-check.yml` runs every 5 min via cron, hits the public `/api/v1/health`. On non-200, sends a Telegram alert to the ops bot (GitHub secrets `OPS_TELEGRAM_BOT_TOKEN`/`OPS_TELEGRAM_CHAT_ID`, see Ops bot split) with HTTP code, response body, and a link to the failed run.
- **Backup alerts (ABA-163)**: `backup-db.yml` posts a Telegram alert on any failed nightly DB backup (`OPS_TELEGRAM_BOT_TOKEN`/`OPS_TELEGRAM_CHAT_ID`), same channel as the uptime check. A silent backup failure is the classic way to discover at restore time that there are no backups — so failures, not successes, are alerted.
- **Infra watch (ABA-165)**: `.github/workflows/infra-watch.yml` — cron every 30 min, SSHes to the VPS and pipes `scripts/infra-check.sh` (`ssh … 'bash -s' < script`) to check root-disk usage (> 85% alerts) and that all 4 prod containers are running and not `unhealthy`; non-zero exit → Telegram alert. Complements `uptime-check.yml` (5-min `/health`) with disk pressure + per-container granularity. Reuses SSH + Telegram secrets (no new ones).
- **Log rotation (ABA-165, gap found in ABA-432)**: `docker-compose.prod.yml` sets `logging` `json-file` `max-size: 10m` / `max-file: 3` on postgres/redis/api/admin (~30 MB/container) so logs can't fill the disk. **That covers only 4 of the 16 containers on the box.** Everything created outside compose has no limit — including **our own** `ai-budget-web-prod` and `ai-budget-app-prod` (hand-created on the VPS in ABA-213/ABA-269) and `shared-nginx`, whose json.log had reached **244 MB** by 2026-08-24. Recreating them with `--log-opt max-size=10m --log-opt max-file=3` is the fix and is **not yet done** (ABA-432); `shared-nginx` needs a window because it briefly interrupts every site on the box. Also left alone deliberately: **`/root/.gradle` 4.3 GB + `/opt/android-sdk` 2.9 GB** of Android toolchain on a server that only runs API/admin/nginx — mobile builds happen on EAS and GitHub runners, so it is almost certainly a leftover, but it may belong to another project.
- **Disaster recovery**: `docs/ops/restore-runbook.md` (DB-only restore) and `docs/ops/disaster-recovery-runbook.md` (full server rebuild after total VPS loss). Both need the offline `age` private key; full rebuild also needs an **offline copy of `.env.production`** (prod secrets live only on the VPS). Redis is cache-only and intentionally not persisted.
- **Errors**: `@sentry/node` v8 captures unhandled exceptions and Express 5xx errors. Init must remain at the top of `main.ts` via `import './instrument'` — moving it after other imports breaks instrumentation.
- **No Prometheus / Datadog / external APM** at this time.
